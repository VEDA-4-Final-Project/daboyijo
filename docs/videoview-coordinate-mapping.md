# VideoView 좌표 매핑 — Phase 4 레이아웃 변경 전 기준선

**작성:** 2026-08-15 · **근거:** `client/videoview.cpp`, `client/videoview.h` 직접 열람
**목적:** STATE.md가 Phase 4의 전제로 걸어둔 항목 — *"`videoview.cpp`의 현재 좌표 매핑 로직. Phase 4 레이아웃 변경 **전에** 문서화 필요 (VERIFY-02의 전제)"*.

레이아웃을 바꾼 뒤 이 문서와 대조해 매핑이 그대로인지 확인한다. 이 문서는 "무엇이 바뀌면 침대 클릭이 깨지는가"에 답하기 위한 것이다.

## 1. 사슬 전체

침대 클릭 한 번이 지나가는 경로:

```
mousePressEvent(e)                     videoview.cpp:411-415
  → toNorm(e->position())              videoview.cpp:208-214   위젯 픽셀 → 0~1 정규화
      → displayRect()                  videoview.cpp:196-206   프레임이 놓이는 사각형
  → zoneAt(normPt)                     videoview.cpp:141-149   0~1 점 → roi_id
  → emit zoneSelected(channel_, hit)   videoview.cpp:414
```

ROI는 **프레임 전체 기준 0~1 정규화**로 저장된다(`RoiZone::poly`, `videoview.h:16-20`). 위젯 픽셀 좌표로는 저장하지 않는다. 이 설계 덕분에 **위젯 크기가 변해도 ROI는 따라 움직인다** — 크기만 바뀌는 변경은 안전하다.

## 2. `displayRect()` — 이 사슬의 유일한 위험 지점

```cpp
QRectF VideoView::displayRect() const {
    if (frame_.isNull()) return QRectF(rect());
    QSizeF fs = frame_.size();
    fs.scale(size(), Qt::KeepAspectRatioByExpanding);   // ← 핵심
    const qreal x = (width()  - fs.width())  / 2.0;
    const qreal y = (height() - fs.height()) / 2.0;
    return QRectF(x, y, fs.width(), fs.height());
}
```

**`KeepAspectRatioByExpanding` = cover + 중앙 크롭이다. 레터박스가 아니다.**

- 프레임이 위젯을 꽉 채우도록 확대되고, 넘치는 부분은 위젯 밖으로 밀려나 잘린다.
- 그래서 `x` 또는 `y`가 **음수**가 되고, `displayRect()`는 위젯 경계를 벗어난 사각형을 돌려준다.
- 반환값은 여전히 "프레임 **전체**의 배치 사각형"이므로, 여기에 대한 0~1 정규화는 서버 `Detection.cx/cy`(프레임 전체 기준 0~1)와 그대로 일치한다. 이 일치가 서버-클라 좌표계 계약의 근거다.

⚠️ **`FramePreview`(같은 파일, `videoview.cpp:483-487`)는 `Qt::KeepAspectRatio`를 쓴다 — 진짜 레터박스다.** 두 클래스의 배치 규칙이 다르다. 카메라 설정 팝업의 클릭-투-포커스 좌표 계산이 이쪽을 쓴다. 혼동하지 말 것.

## 3. 무엇이 바뀌면 깨지는가

| 레이아웃 변경 | 매핑 영향 | 위험도 |
|---|---|---|
| 영상 셀의 **크기만** 변경 (가로세로 비율 유지) | 없음. 프레임 전체가 같은 비율로 확대/축소되고 크롭 영역도 동일 | 안전 |
| 영상 셀의 **가로세로 비율** 변경 | **크롭되는 영역이 달라진다.** 이전에 보이던 프레임 가장자리가 위젯 밖으로 밀려난다 | **높음** |
| 셀 위치·여백·부모 레이아웃 변경 | 없음. 모든 계산이 위젯 로컬 좌표(`size()`, `e->position()`) 기준 | 안전 |
| `cornerRadius_` 변경 | 없음. `paintEvent`의 클리핑에만 쓰이고 좌표 변환에는 안 쓰인다 | 안전 |

**가장 위험한 시나리오 (비율 변경):** ROI 폴리곤 자체는 프레임 기준이라 안 움직인다. 하지만 크롭으로 잘려나간 영역은 **위젯 위에 존재하지 않으므로 클릭할 수 없다.** 즉 화면 가장자리에 걸친 침대가 **조용히 선택 불가능해진다** — 에러도, 로그도 없다. 클릭해도 아무 일이 안 일어날 뿐이다.

`toNorm()`의 `qBound(0.0, nx, 1.0)`(`videoview.cpp:213`)이 이 실패를 더 조용하게 만든다: 크롭 밖을 겨냥한 클릭은 미스로 처리되지 않고 **가장 가까운 경계값으로 클램프**되어, 운이 나쁘면 **가장자리의 엉뚱한 ROI가 잡힌다.** 안 잡히는 것보다 나쁜 실패 모드다.

### 3.1 그런데 이 조건은 이미 상시로 일어나고 있다 (2026-08-15 정정)

`videoCard`는 `setMinimumSize(140, 96)`만 지정하고(`mainwindow.cpp:1214`) 그리드는 행·열 stretch를 1:1로 준다(`mainwindow.cpp:1259-1262`). **셀 비율이 고정돼 있지 않다** — 창 크기가 바뀌면 셀 비율이 따라 바뀌고, 크롭 영역도 따라 바뀐다.

따라서 "크롭이 달라지는 상황"은 Phase 4가 새로 만드는 위험이 아니라 **사용자가 창을 리사이즈할 때마다 이미 일어나는 기존 조건**이다. 처음 작성 시 이를 Phase 4 고유의 위험으로 서술했던 것은 오류다.

실질적 함의:
- **"셀 비율을 고정하라"는 제약은 실현 불가능하고 필요하지도 않다.** 현재 설계가 애초에 가변이다.
- 남는 진짜 제약은 **정도**의 문제다: 셀을 현재 운용 범위에서 크게 벗어난 비율(예: 아주 납작하고 넓은 칸)로 만들면 크롭이 심해져 도달 불가능한 프레임 영역이 커진다.
- 이 계열의 회귀는 Phase 4가 아니라 **`displayRect()`의 cover-crop + `qBound` 클램프 조합 자체**에서 나온다. 근본 해법(크롭 밖 클릭을 미스로 처리)은 좌표계 변경이라 v1 범위 밖이다.

## 4. Phase 4가 지켜야 할 것

1. **셀 비율을 현재 운용 범위에서 크게 벗어나게 만들지 말 것.** 대략 2×2 균등 분할이 만들어내는 비율대(창 크기에 따라 변동)를 유지한다. 극단적으로 납작하거나 홀쭉한 칸은 크롭을 키운다. 그리드 재배치·여백 변경·패널 폭 조정 자체는 안전하다.
2. **`displayRect()` / `toNorm()` / `toWidget()` / `zoneAt()` 네 함수를 수정하지 말 것.** Phase 4는 레이아웃 단계이지 좌표계 단계가 아니다. 이 넷 중 하나라도 diff에 나타나면 VERIFY-02를 전면 재수행한다.
3. **`VideoView`를 다른 부모로 옮기거나 크기 정책을 바꾸는 것 자체는 안전하다** — 모든 계산이 위젯 로컬이다.
4. **스포트라이트 모드(`setVideoFocus`)를 잊지 말 것.** 한 채널을 크게 띄우면 그 셀의 비율이 균등 배치와 크게 달라진다 — 이미 존재하는 경로이고, VERIFY-02 표본에 **스포트라이트 상태의 클릭 확인을 포함**해야 한다.

## 5. VERIFY-02 절차 (전·후 동일하게 수행)

레이아웃 변경 **전에 한 번, 후에 한 번** 같은 침대·같은 지점으로 수행하고 결과를 나란히 기록한다.

1. 앱을 띄우고 ROI가 등록된 채널을 연다.
2. 각 침대의 **중앙**을 클릭 → 인스펙터에 그 침대가 선택되는지 확인.
3. 각 침대의 **경계 안쪽 가장자리**를 클릭 → 같은 침대가 선택되는지 확인.
4. **화면 가장자리에 가장 가까운 침대**를 반드시 포함할 것 — 크롭 실패가 여기서만 드러난다.
5. 침대가 없는 빈 곳을 클릭 → 선택이 해제되는지(`roiId=-1`) 확인.
6. 채널마다 반복.

**실패 판정:** 클릭한 침대와 다른 침대가 선택되거나, 클릭해도 아무 반응이 없거나, 빈 곳 클릭에 침대가 잡히면 실패.
