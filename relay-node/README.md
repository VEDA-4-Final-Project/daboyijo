# 📡 relay-node — 중계 노드 (Raspberry Pi 4)

**웨어러블의 BLE 신호를 받아 MQTT 브로커로 넘기는 게이트웨이**

> 입소자가 손목에 찬 STM32 웨어러블이 심박·산소포화도·걸음 수를 재고 넘어짐도 감지합니다.
> 그 값을 무선으로 받아 브로커에 올리는 것이 이 노드의 전부입니다.
> **판정과 알람은 서버가 맡고, 여기는 중계만 합니다.**

- **담당**: 김예훈, 이교민, 전승현

---

## 1. 하는 일

```
STM32 ──UART(9600)──> HM-10 ──BLE──> RPi4 (relay_node) ──MQTT──> 브로커 ──> master_node
```

가운데 **HM-10** 은 BLE 시리얼 모듈입니다. STM32 가 UART 로 뱉은 바이트를 그대로
BLE 로 흘려보내 주는 부품이라, 파이 입장에서는 "블루투스로 연결하면 7바이트씩
계속 밀어 주는 기기" 로 보입니다.

| 역할 | 내용 |
| --- | --- |
| **연결 유지** | HM-10 에 BLE 로 붙고 끊기면 재연결 (`FFE1` 특성의 notify 구독) |
| **패킷 재조립** | 조각나서 도착하는 바이트를 7바이트로 맞추고 체크섬 검증 |
| **버퍼링** | 브로커가 끊겨 있으면 내부 큐에 쌓고, 재연결 시 한꺼번에 발행 |
| **타임스탬프** | 받은 시각을 붙임 (패킷 안에는 시각 필드가 없음) |
| **중복 억제** | 낙상은 **상승엣지(0→1)** 일 때만 발행 (4절) |

---

## 2. 빌드 · 실행

```bash
./install_deps.sh                      # 최초 1회
cmake -S . -B build && cmake --build build
./relay_node                           # 실행 파일은 relay-node/ 에 생깁니다
```

| 의존성 | 설치 방법 |
| --- | --- |
| `libmosquitto` | apt |
| `nlohmann_json` | apt |
| `SimpleBLE` | apt 패키지가 없어 `install_deps.sh` 가 소스에서 빌드해 `/usr/local` 에 설치 |

CMake 가 `find_package(simpleble)` 로 찾으므로 한 번 설치하면 소스 트리는 필요 없습니다.

> 실행 파일이 `build/` 가 아니라 `relay-node/` 에 생기는 것은 의도한 것입니다.
> 설정 파일을 실행 파일 옆에서 찾는데, `build/` 는 지웠다 다시 만드는 곳이라
> 거기에 설정을 둘 수 없습니다.

## 3. 설정

`relay-node.conf` 를 실행 파일과 같은 디렉터리에서 읽습니다. `-c 경로` 로 다른
파일을 지정할 수 있습니다. 파일이 없으면 기본값으로 뜨고 그 사실을 출력합니다.

```
broker_host  = localhost       # 배치할 때 서버 IP 로
broker_port  = 8883            # MQTTS — 평문으로 되돌리려면 1883 + ca_path 비우기
ca_path      = certs/ca.crt    # 브로커 검증용 CA, 비우면 평문. git 에 안 올라갑니다
device_id    = wearable_01     # WearableData.device_id
topic        = veda/wearable/data
hm10_addr    = 88:4a:ea:62:0b:03   # 모듈을 교체하면 여기만 고칩니다
scan_ms      = 8000            # 스캔 제한 시간
reconnect_ms = 3000            # 끊긴 뒤 재시도 간격
debug_hex    = 0               # 1 이면 수신 원시 바이트를 hex 로 덤프
```

- **`ca_path` 는 실행 파일 기준 상대 경로입니다.** 인증서는 저장소에 없으니 기기마다
  직접 배치해야 합니다. 비우면 평문, 채우면 MQTTS 로 붙습니다.
- **호스트명 검증은 꺼 두었습니다.** 브로커 IP 는 DHCP 로 바뀌는데 인증서에 적힌
  이름은 고정이라, 켜 두면 주소가 바뀔 때마다 연결이 깨집니다.
- **`FFE0`/`FFE1` UUID 와 7바이트 규격은 설정으로 빼지 않았습니다.** 기기가 바뀌어도
  같은 값이고, 이게 바뀐다면 코드도 같이 바뀌어야 하는 규격입니다.

## 4. 받는 것 — 7바이트 패킷

`firmware/App/Drivers/hm10.h` 와 같은 규격입니다.

| 오프셋 | 필드 | 범위 |
| --- | --- | --- |
| 0 | 헤더 `0xAA` | 고정 |
| 1 | `heart_rate` (bpm) | 0~255 |
| 2 | `spo2` (%) | 0~100 |
| 3 | `fall_flag` | 0 / 1 |
| 4~5 | `steps` (리틀엔디언 uint16) | 0~65535 |
| 6 | `checksum` | `[0]~[5]` 의 XOR |

예시: `AA 4E 62 01 E8 03 6C` = 78bpm, 98%, 낙상 의심, 1000걸음

원래는 5바이트였는데 **체온을 빼고 걸음 수와 체크섬을 넣었습니다.** 체온은 재는
하드웨어가 아예 없어서 0 만 실려 나갔고, 그 0 때문에 받는 쪽의 체온 판정(서버
40도 알람, Qt 38도 위험)이 한 번도 발동한 적이 없었습니다.

> ⚠️ **펌웨어와 이 노드는 반드시 같이 배포해야 합니다.** 길이가 어긋나면 패킷
> 경계를 잘못 잡습니다. 한쪽만 올리면 다음 패킷의 헤더까지 현재 패킷으로
> 삼키거나, 남는 바이트가 `0xAA`(170) 일 때 가짜 헤더로 오인합니다.

### ⚠️ 체크섬은 오류 검출이 아니라 경계 찾기용입니다

전송 중에 값이 깨졌는지 보려고 넣은 것이 아닙니다. BLE 가 이미 링크 계층에서
CRC 와 재전송으로 무결성을 보장하기 때문에 그쪽은 걱정할 필요가 없습니다.

진짜 문제는 **"패킷이 어디서 시작하는가"** 입니다. 받는 쪽은 `0xAA` 를 찾아 패킷
시작으로 삼는데, 헤더가 아닌 데이터 바이트에도 `0xAA`(170) 가 나올 수
있습니다(걸음 수가 170, 426, 682… 일 때). 그러면 엉뚱한 자리를 시작으로 잡고 그
뒤가 통째로 밀립니다. 체크섬이 이걸 바로 잡아내서 **1바이트 밀고 다시 맞춥니다.**

우연히 통과할 확률은 **1/256 으로 CRC-8 과 같은 수준**입니다. 1바이트 검사의
한계이고, 어긋나는 일이 실제로 잦아지면 그때 폭을 늘리면 됩니다.

필드 범위 검사도 남아 있지만 역할이 바뀌었습니다. 경계 찾기는 체크섬이 책임지고,
범위 검사는 **보내는 쪽 논리 오류**(범위 밖 값을 싣는 펌웨어 버그)를 잡는 보조
수단입니다. 그래서 체크섬은 맞는데 범위를 벗어나면 조용히 버리지 않고 `stderr`
에 남깁니다.

### 낙상은 상승엣지만 발행합니다

펌웨어는 **1Hz 주기**로 보내고, 낙상이 확정되면 주기를 기다리지 않고 즉시 한 번
더 보냅니다.

주의할 점은 `fall_flag` 가 "방금 넘어졌다" 가 아니라 **"지금 넘어진 상태다"** 라는
것입니다. 확정 후 5초 동안 계속 1 로 유지됩니다(`HM10_FALL_HOLD_MS`). 그대로
흘리면 낙상 한 건에 알람이 5~6번 뜨기 때문에, 이 노드가 **0 에서 1 로 바뀌는
순간만** 낙상으로 발행합니다.

## 5. 보내는 것 — MQTT 발행

토픽 `veda/wearable/data`, payload 는 `WearableData` JSON 입니다.

```json
{"device_id":"wearable_01","is_fall_detected":false,
 "heart_rate":78,"spo2":98,"steps":1000,"timestamp":1754000000000}
```

| 종류 | QoS | 이유 |
| --- | --- | --- |
| 바이탈 (`is_fall_detected: false`) | **0** | 빠르게, 하나쯤 놓쳐도 다음 게 옵니다 |
| 낙상 (`is_fall_detected: true`) | **1** | 반드시 전달 |

## 7. 트러블슈팅

| 증상 | 확인할 것 |
| --- | --- |
| 값이 이상하게 들어옴 | `debug_hex = 1` 로 두면 파싱 전 원시 바이트를 hex 로 덤프합니다 (예전 환경변수 `RELAY_DEBUG_HEX` 대체) |
| 계속 재연결만 반복 | `hm10_addr` 의 MAC 이 맞는지, 모듈을 교체하지 않았는지 |
| TLS 연결 실패 | `ca_path` 가 가리키는 인증서가 기기에 실제로 있는지 (실행 파일 기준 상대 경로) |
| 낙상 알람이 여러 번 뜸 | 상승엣지 판정이 도는지(4절). 펌웨어만 올리고 노드를 안 올렸을 수 있습니다 |

### 알려진 제약

- **체온은 지원하지 않습니다.** 재는 하드웨어가 없어 구현된 적이 없고, 펌웨어
  패킷과 `WearableData` 양쪽에서 제거했습니다.
- **심박과 걸음 수는 범위 검증을 하지 않습니다.** 0~255, 0~65535 전체가 유효한
  값이라 검사할 근거가 없습니다. 경계 찾기는 체크섬이 맡으므로 문제되지 않습니다.
